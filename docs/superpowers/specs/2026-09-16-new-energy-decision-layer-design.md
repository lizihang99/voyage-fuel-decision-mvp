# 新能源混兑经济性决策层设计

> 状态：待审核
>
> 日期：2026-09-16
>
> 本文定义金老师提出的“加入新能源燃料后，计算多花多少钱、节省多少碳税、需要加入多少新能源燃料”的第一阶段实现边界。本文只增加决策层，不改变现有单航次计算内核的公式、输入含义和既有结果。

## 1. 目标

在现有燃料、能源、排放、EU ETS、FuelEU 和方案比较能力之上，增加新能源替代决策：

- 用户可以选择现有燃料目录中的一种或多种新能源候选燃料；
- 系统自动计算候选燃料在不同混兑比例下的航段用量；
- 系统比较新能源方案与 B0 基准方案的燃料成本、EU ETS 成本和净成本；
- 系统展示 FuelEU 指标和航次级指示性金额的变化；
- 系统给出可解释的推荐用量、质量比例和推荐原因。

本功能直接对应以下业务问题：

```text
新能源燃料贵多少？
可以节省多少 EU ETS 成本？
FuelEU 指标改善多少？
最终净成本增加还是减少？
在约束条件下需要加入多少新能源燃料？
```

## 2. 与现有系统的关系

现有 `calculate_voyage()` 和案例级计算能力继续作为唯一计算来源，负责：

- B0 物理能源；
- 燃料质量和质量混兑反算；
- EU ETS 排放、EUAs 和 EUA 成本；
- FuelEU GHGI、目标、合规余额和指示性金额；
- 单个候选方案的约束和目标计算。

新增决策层只负责：

```text
读取案例输入
-> 生成新能源候选方案
-> 调用现有计算器
-> 计算相对 B0 的变化
-> 过滤不可比较方案
-> 排序并生成条件式推荐
-> 将同一结果交给页面、CSV 和 PDF
```

决策层不得复制或重新实现能源、排放、EU ETS、FuelEU 公式。页面不得自行计算成本、节省金额或推荐比例。

## 3. 第一阶段范围

### 3.1 支持内容

- 使用现有燃料因子目录中的新能源路径；
- 同一案例支持多个独立新能源候选；
- 每个候选由一种基准燃料和一种候选燃料组成；
- 使用现有质量混兑比例定义；
- 使用现有燃料价格、EUA 价格、供应量、预算和最大混兑比例；
- 自动搜索 `[0, xCap]` 内的关键比例和固定报告方案；
- 展示新增燃料成本、EU ETS 成本节省、FuelEU 变化和净成本变化；
- 分别给出成本优先、达标优先和减排优先结果；
- 保留 B0 作为所有经济比较的基准。

### 3.2 暂不支持

- 本阶段新增燃料因子或虚构新能源数据；
- 任意三种及以上燃料的同时混兑；
- 正式年度 FuelEU 罚款或年度船队合规；
- 多航次年度汇总、Banking、Borrowing、Pooling；
- OPS、岸电和港口停留期新能源用量；
- 采购合同、供应商报价、燃料兼容性或实际交付判断；
- 将 FuelEU 指示性金额直接作为当前模型成本或现金节省；
- 独立物理生命周期 WtW 计算。

“支持多种新能源”在本阶段的含义是：从现有燃料目录选择多个已有候选，逐个生成方案并比较；不要求现在扩充燃料数据库。后续新增燃料时，必须先完成因子、单位、资格、设备和来源证据，再自动进入决策层。

## 4. 输入契约

沿用现有案例输入。新增或明确使用的字段如下：

| 字段 | 含义 |
| --- | --- |
| `candidateFuelPathId` | 现有目录中的新能源候选路径 |
| `candidatePricePerTonne` | 候选新能源燃料价格 |
| `specifiedBlendRatios` | 用户指定的比较比例，可为空 |
| `maxBlendRatio` | 最大质量混兑比例 |
| `candidateSupplyTonnes` | 候选燃料在本航段可用量 |
| `incrementalBudget` | 相对 B0 的当前模型成本增量上限 |

缺少价格时，系统仍计算能源、排放和 FuelEU，但不生成经济排序或“值得使用”的成本结论。缺少候选燃料因子时，只阻断该候选，不影响 B0 和其他候选。

混兑比例始终解释为：

```text
候选燃料质量 / 混合燃料总质量
```

页面必须使用“候选燃料质量占比”这一明确文案，不使用可能产生歧义的 `B20`。

## 5. 方案生成和自动搜索

对每个候选燃料：

1. 始终生成 B0；
2. 如果候选允许纯用，生成 B100 参考方案；
3. 生成用户指定的比例；
4. 计算达到年度 GHGI 目标所需的最低比例；
5. 计算预算、供应量和最大混兑比例形成的有效上限；
6. 生成约束下的最大合规改善方案；
7. 对重复比例去重后形成固定报告方案集合。

连续比例只用于求解边界和最优比例，不把大量连续点全部展示给用户。所有方案必须保持与 B0 相同的物理能源需求。

推荐比例不得由页面显示精度决定。内部使用未舍入值，显示时再格式化；最低达标比例向可行侧取值，避免页面显示为达标但内部实际未达标。

## 6. 经济性口径

当前模型成本固定为：

```text
当前模型成本 = 燃料采购成本 + EU ETS 成本
```

相对 B0 的核心结果为：

```text
新增燃料成本 = 新能源方案燃料成本 - B0燃料成本
EU ETS成本节省 = B0 EU ETS成本 - 新能源方案 EU ETS成本
净成本变化 = 新能源方案当前模型成本 - B0当前模型成本
```

因此：

- 净成本变化小于 0：新能源方案在当前模型下更便宜；
- 净成本变化等于 0：两者当前模型成本相同；
- 净成本变化大于 0：新能源方案需要额外支付成本。

FuelEU 指标改善单独展示：

- GHGI 变化；
- 合规余额变化；
- 指示性金额变化。

FuelEU 指示性金额不进入当前模型成本、预算约束、默认成本排序或“现金节省”字段。

## 7. 推荐规则

不生成没有目标依据的单一“综合最优”。系统提供三类可解释结果：

### 7.1 成本优先

在价格完整、方案可行且状态为 `COMPARABLE` 时，选择当前模型成本最低的方案。该结果回答：

```text
只看燃料成本和 EU ETS 成本，哪个方案最省钱？
```

### 7.2 达标优先

在目标适用且存在可达方案时，选择达到当年 GHGI 目标的最低当前模型成本方案，并展示最低达标比例。

该结果回答：

```text
满足目标至少需要加入多少新能源？其中哪个方案成本最低？
```

### 7.3 减排优先

在 FuelEU 适用且候选可以改善 GHGI 时，选择约束范围内合规余额改善最大的方案，并同时展示其净成本变化。

该结果回答：

```text
在供应量、预算和最大混兑比例限制下，最多可以改善多少？
```

每个推荐必须携带方案 ID、候选燃料、比例、数量、推荐类型、触发条件、计算状态和执行状态。执行状态继续为 `EXECUTION_CONDITIONS_PENDING`，推荐不代表已完成采购或实际可执行。

## 8. 结果展示

页面至少展示以下内容：

| 结果区 | 必须回答的问题 |
| --- | --- |
| 基准方案 B0 | 现有方案花多少钱、排放多少 |
| 新能源用量 | 需要加入多少吨、占总质量多少 |
| 新增燃料成本 | 因使用新能源多花多少钱 |
| EU ETS 成本变化 | 少支付多少或多支付多少 EUA 成本 |
| FuelEU 变化 | GHGI、合规余额和指示性金额如何变化 |
| 净成本变化 | 最终多花还是省钱 |
| 推荐方案 | 在何种目标和约束下推荐该方案 |

方案表必须同时展示绝对值和相对 B0 的变化。用户可以区分：

- “新能源改善了合规指标”；
- “新能源降低了 EU ETS 成本”；
- “新能源在当前价格下是否经济”。

页面、CSV 和 PDF 都消费同一份原始 `DecisionCaseResult`，不能分别重新计算。

## 9. 兼容性和安全边界

### 9.1 旧功能不变

- 新功能默认可关闭或仅在存在候选新能源时生效；
- 没有新能源候选时，现有 B0、单候选和案例级结果保持不变；
- 新能源比例为 `0` 时，结果必须与 B0 数值一致；
- 不修改既有函数的输入含义和公开返回字段；
- 旧 API、旧导出格式和旧页面流程继续可用；
- 页面显示精度调整不得改变原始结果、排序、状态或推荐。

### 9.2 错误隔离

- 单个新能源候选因因子、价格或约束错误时，只标记该候选；
- B0 或港口基础数据错误时，按既有规则阻断整个案例；
- 经济输入缺失不阻断能源、排放和合规计算；
- 未验证的新能源因子继续标记 `ESTIMATED`；
- 所有结果继续显示 `EXECUTION_CONDITIONS_PENDING`。

### 9.3 版本和追溯

新增结果必须携带现有计算规格版本、燃料因子版本、港口规则版本和来源 ID。决策层不得覆盖底层因子证据状态。

## 10. 测试和验收

### 10.1 旧功能回归

- 现有单航次计算测试全部通过；
- 现有案例比较测试全部通过；
- 现有 API、网页、CSV、PDF 测试全部通过；
- 现有 Node 港口测试全部通过；
- 现有 E2E 流程不因新增控件改变结果；
- `0%` 新能源方案与 B0 逐字段一致。

### 10.2 新功能测试

至少覆盖：

1. 一个已有新能源候选的成本对比；
2. 多个已有新能源候选的独立比较；
3. 新能源价格高于 B0 但 EU ETS 成本下降；
4. 新能源价格低于 B0 且净成本下降；
5. 自动找到最低达标比例；
6. 供应量限制、预算限制和最大混兑限制；
7. 没有达到目标的候选；
8. 价格缺失但排放和 FuelEU 仍可计算；
9. 候选因子错误不影响其他候选；
10. 成本优先、达标优先和减排优先推荐；
11. FuelEU 指示性金额不进入当前模型成本和排序；
12. 页面、CSV、PDF 使用相同原始结果；
13. 显示精度改变不影响排序和推荐；
14. 结果中明确显示用量、比例、成本、节省和净变化。

## 11. 开发顺序

1. 先冻结输入、输出、公式和推荐规则；
2. 建立“没有新能源候选时结果不变”的回归测试；
3. 增加新能源方案生成和自动搜索；
4. 增加成本、节省和净变化字段；
5. 增加三类推荐结果；
6. 接入 API、页面、CSV 和 PDF；
7. 完成旧功能回归和新功能测试；
8. 使用至少一个真实业务案例验收；
9. 代码审查通过后再合并 `main`。

每个阶段单独提交，提交前运行对应聚焦测试；最终合并前运行完整验收矩阵。任何旧功能回归失败都暂停合并，不通过增加兼容分支掩盖问题。

## 12. 完成标准

只有同时满足以下条件，才认为金老师要求的第一阶段功能完成：

- 可以从现有燃料目录选择一种或多种新能源候选；
- 系统可以自动计算达到目标或受约束情况下的新能源用量；
- 页面清楚展示新增燃料成本、EU ETS 成本节省、FuelEU 变化和净成本；
- 页面给出有条件、有依据的推荐方案；
- FuelEU 航次级估算边界没有被误写成正式年度罚款；
- 没有新能源候选时旧功能结果不变；
- 新旧测试全部通过；
- 真实案例可以复核每一个推荐结果的输入、单位、公式和来源。
